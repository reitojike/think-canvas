# ThinkCanvas Constitution

## 基本原則

### I. 製品要件の authority と判断の追跡

製品の意図、利用者の課題、制約については PRD を authority とします。HTML モックは
操作の reference implementation であり、新しい要件の根拠にはしません。両者が食い違う場合、
spec は PRD に従い、差分を記録しなければなりません。PRD が決めていない事項は、実装前に
機能の spec で判断と理由を明記しなければなりません。PRD と HTML モック自体は
この公開リポジトリに追加しません。

### II. Standard-First, Not Standard-Always

原則は `standard-first, not standard-always` です。Android の標準動作、Jetpack の指針、
アクセシビリティ、利用者に馴染みのある操作を出発点とします。製品の意図に合う標準パターンは
採用しなければなりません。自由な空間配置や明示された要件を妨げる場合は、代替案、理由、
アクセシビリティへの影響、適用範囲を Living Spec または architecture に記録しなければなりません。
例外は対象の操作に限定し、レビューできる形にします。

### III. 空間配置は利用者の情報

キャンバス上の位置と相対配置は、利用者の思考を表す情報として保持しなければなりません。
機能の spec と利用者の明示的な操作なしに、自動整列、吸着、分類、再配置を行ってはなりません。
viewport の移動や表示環境の変化によって、保存された位置関係を暗黙に変更してはなりません。
余白と配置に利用者が与えた意味を守るための規則です。

### IV. ローカル優先と要求時のみの AI

記録、閲覧、編集、保存の基本操作は、AI サービスやアカウントなしで端末上で完結しなければ
なりません。利用者の内容は、既定で端末内に保存します。AI は利用者が明示的に要求したとき
だけ動作し、使用する情報と結果の変更を利用者が確認・制御できなければなりません。
キャンバスの内容を暗黙に送信したり、基本操作の完了に AI を必須としたりしてはなりません。

### V. 機能設計より先に仕様を定める

機能のコードを書く前に、該当する Living Spec で観測できる振る舞いを決めなければなりません。
現在の製品仕様は `specs/**/spec.md`、技術設計は `docs/architecture/`、継続的な運用手順は
`docs/runbooks/` に置きます。変更の目的・範囲・計画・作業一覧・差分・検証結果は Issue / PR に
記録します。既存機能は既存の仕様を更新し、作業ごとの仕様ディレクトリを増やしません。
衝突と未決事項は実装前に解消しなければなりません。Spec Kit の一時成果物は作業の補助であり、
そのまま現行仕様の正本にはしません。

## 技術上・公開上の制約

- Android アプリには Kotlin と Jetpack Compose を使用します。Jetpack Ink を描画ツール、
  Room 3 を端末内保存のライブラリとして採用する方針です。依存関係と schema は、対応する
  機能の spec で使用方法が決まってから追加します。
- 依存ライブラリとビルドツールの導入・更新では、公開済みの最新安定版を出発点とします。
  互換性と検証結果から採用版を決め、保留する場合は理由を Issue または PR に記録します。
  再現可能なビルドのため、動的バージョンは使いません。
- タッチ領域、semantics、文字の読みやすさ、gesture 以外の操作手段を含め、すべての機能で
  Android のアクセシビリティを考慮しなければなりません。
- API キー、トークン、認証情報、個人情報、ローカルパス、非公開サービス情報、会話ログ、
  PRD、HTML モックを公開リポジトリに追加してはなりません。ローカル設定と生成された
  ビルド成果物は追跡対象から除外します。公開前に、変更内容がこの境界を守るか確認します。

## 開発手順

- Issue で変更範囲・対象外・受け入れ条件・停止条件を先に定めます。現在の仕様を読み、
  曖昧さの解消、設計、作業分割、整合性確認、実装、検証・レビューの順で進めます。
- Spec Kit の標準ワークフローは必要に応じて使います。成果物はタスク内に留め、必要な
  現在仕様・設計・手順だけをそれぞれの正本へ反映します。未完了タスク表や実行ログを残しません。
- 設計では Constitution との整合を確認します。Android 標準から外れる理由と、影響・
  アクセシビリティへの対応を残します。検討経緯や不採用案は Issue / PR で追跡します。
- 観測可能な受け入れ条件を検証し、結果と残る差分を Issue / PR に記録してから完了を判定します。
  保存と空間配置の不変条件は意味のあるテストで確認します。検証・レビューの合格条件は
  既存の runbook に従い、この文書整理によって省略しません。

## 運用と改訂

この Constitution はリポジトリの仕様、設計、実装、レビューに適用します。改訂時は理由、
影響する原則、既存の仕様への影響、必要な移行作業を明記しなければなりません。版には
semantic versioning を使い、原則の互換性を壊す変更は MAJOR、新しい原則や重要な規則の追加は
MINOR、意味を変えない明確化は PATCH とします。公開する変更は、現行の Constitution と
公開情報の境界に照らして確認します。製品要件の authority は PRD にあり、この Constitution は
要件を解釈し実装する際の規則を定めます。

改訂理由・移行範囲は [Issue #205](https://github.com/reitojike/think-canvas/issues/205) と関連 PR、
以前の版は Git 履歴で追跡します。文書の置き場所と作業成果物の扱いを変更しており、製品の
機能・保存契約・検証条件は変えません。
